# Grounded Commits: landing

Format version 0.3.3. This part is optional: the commit and pull-request conventions work under any merge method. What is not optional is knowing what your method does to the commits, because they are the record: their messages, the trees their evidence lines describe, and their signatures. This document says what each method does and how to land so that what reaches the target is what was reviewed and checked.

## What landing has to preserve

1. **The commits.** The reviewed commits land as the objects they were reviewed as: same hashes, same trees, same messages, same signatures. A method that replays them as new objects gives every one a new tree, so every `Verified: final contents` on the branch describes a tree that was never tested and every author signature is gone; the branch then owes a re-run or a rebinding per commit (`commit-messages.md`, *After a rewrite*) and a re-signing, and the reviewers approved objects that no longer exist.
2. **The landed tree is checked.** Integrating a branch with a target that has moved produces a tree no branch commit has. That tree is checked before it lands, as the object that lands, and the commit that carries it says so in its own `Verified:` line.
3. **Nothing from the pull-request body enters history.** The body is a review brief. The merge commit carries Git's subject, its evidence pair, the pull request's URL under `Refs:` and the reviewer trailers the forge or the landing writes, and a body only where it resolved something.
4. **Issues close by hand after landing**, never by keyword.

## The integration candidate

The method that preserves all four lands a candidate built before landing: a merge commit `C` whose first parent is the target's tip `B` and whose second is the approved head `H`, made with `--no-ff` so that it exists even when `B` is already an ancestor of `H`. Its tree is the branch integrated into the target as the target stands. The landing agent builds it, runs the repository's checks on it, writes its message (Git's subject; a trailer block with `Verified: final contents; <checks>; <outcome>`, `Refs: <pull request URL>` and the `Reviewed-by:` or `Reviewed-on:` lines the forge supplies; a body only where a conflict was resolved, saying how), signs it as the repository signs commits, and advances the target to exactly `C`. If the target moved meanwhile, the advance is refused: build `C' = merge(B', H)`, check it, try again; never force. When `B` is already an ancestor of `H`, `C`'s tree is `H`'s, so the checks that ran on `H` ran on the landed tree, and `C`'s `Verified:` line may name them as such.

Making the merge commit even then is deliberate: it gives `git log --first-parent` one commit per pull request, and it is the one place for the pull request's URL and the integration's evidence that needs no rewrite of a reviewed commit. A repository that prefers to fast-forward the target to `H` itself when `H` already contains `B` records that in its guidance; it then has no commit to carry the URL, and lands a merge commit only for a branch that is behind.

A stacked pull request lands the same way: once its parent has landed, the child is retargeted to the target and its candidate is built from its own head, whose commits were never rewritten. A forge's own stacked-pull-request feature that rebases the stack at each landing is not used.

## Why not the other methods

- **Rebase, by the forge or by hand, then fast-forward.** Replays every commit: new hashes and trees, author signatures dropped (a forge cannot sign with the author's key; a local rebase re-signs only with signing on, and plumbing such as `git commit-tree` never signs), and every `Verified: final contents` rebound. Reviewers approved commits that are no longer what lands, and a re-check of the tip covers the tip alone. Linear history is all it buys.
- **Squash.** One new commit; every branch commit's message, evidence and signature is gone, and the trailer blocks of all but the last are buried in a body Git does not read as trailers. Supported where a repository wants one commit per pull request: the landing agent composes the message in the commit format from the branch's commits, with the evidence rebound to the landed tree, and supplies it explicitly, never the forge's default and never the pull-request body.
- **A merge the forge makes of a stale branch.** The forge's checks ran on a temporary merge of the head into the target as it stood when the run started, and recorded the result against the head's hash. A target that moves afterwards leaves that result green and re-runs nothing, so the merge the forge then makes has a tree nobody checked. That gap is why forges offer an up-to-date rule and a merge queue; without one of them it is open.

## Per forge

| Forge | Settings | Landing |
|---|---|---|
| **GitHub**, organisation-owned repository | Merge commits only; "Require linear history" off. A ruleset on the target: require a pull request; required status checks; "Require merge queue" with merge method *merge* and "Only merge non-failing pull requests"; block force pushes. Every required workflow triggers on `pull_request` and `merge_group`. | After approval, enqueue the approved head: `gh pr merge <n> --auto --match-head-commit <H>`, or the API's asynchronous merge with `sha` and `merge_action: merge_queue`. The queue builds the merge, runs the `merge_group` workflows on it and lands that commit; the `merge_group` run on the landed hash is its evidence, and the `#N` in its subject the pull request's handle. The queue's commit carries GitHub's message and signature, so the agent adds no trailers to it. No bypass. Wait for the merge itself; an enqueued state is not a landing. |
| **GitHub**, user-owned repository or no queue | Merge commits only; require a pull request; required checks with "Require branches to be up to date before merging"; block force pushes. | Bring a branch that is behind current with "Update with merge commit", never "Update with rebase"; its merge's tree is then its head's, so the head's checks cover what lands. Land with `gh pr merge --merge --match-head-commit <H>`, or the API's merge with `merge_method: merge` and `sha: <H>` and a `commit_message` carrying the trailers. Each landing on a busy target invalidates every other open pull request's currency; a target taking several pull requests an hour wants a queue. |
| **Forgejo** and **Gitea** | Merge style *fast-forward-only* allowed and default, and *merge* for forks; `DEFAULT_UPDATE_STYLE = merge`. Branch protection: no direct push, or only the landing identity; required status contexts; required approvals; "Require signed commits" where the repository signs. | Build `C` locally, check it, sign it, push it to the pull-request branch (a fast-forward of `H`, which is its parent); the forge runs the pull-request workflows on `C` and records their statuses against it. Land with `POST /repos/{owner}/{repo}/pulls/{index}/merge`, `Do: fast-forward-only`, `head_commit_id: <C>`. The forge refuses a branch that is behind and advances the target to `C` exactly; read back that `merged_commit_id` is `C`. A fork the agent cannot push to: where `H` already contains the target, land by `merge` with `head_commit_id: <H>` and the trailers in `MergeMessageField`; otherwise ask the contributor to update by merge, or publish `C` on a maintainer-owned branch through its own pull request. |
| **GitLab** | Merge method *fast-forward*, automatic rebase off, squash "Do not allow"; or, on Premium or Ultimate with a busy target, merge commits with merged results pipelines and merge trains. | Fast-forward: stage `C` on the source branch as on Forgejo, let the pipeline run on it, land with `PUT …/merge` and `sha: <C>`; GitLab refuses unless `C` contains the target's tip. Trains: add with `auto_merge`; the landed merge is a fresh object whose tree equals the train's checked tree because the train serialises the target. Never the interface's rebase, which runs server-side and drops signatures. |
| **Plain Git**, no forge gate | — | On the target's tip, `git merge --no-ff <H>`, check, write the message, push; a refused push means the target moved, so rebuild. |

Enable only the method your repository uses, so an agent cannot pick another. Whenever a forge makes the landing commit, read its message back (`git show -s --format=%B`, `git interpret-trailers --parse --no-divider`) and confirm the landed tip's second parent is the approved head.

## Pull requests from forks

A fork's commits may not follow the format, and the contributor's branch may not accept the maintainer's push. Record one route in guidance: land the contributor's commits as written through a candidate on a maintainer-owned branch, which preserves their objects; squash with a message composed in the format, the usual route for drive-by contributions; or ask the contributor to fold and reword. Whatever the route, the forge must record the pull request as merged: GitHub does so when the head's commits become reachable from the base, Forgejo and Gitea when the merge goes through their interface or API.

## Forge configuration, in short

- Merge commits enabled; the forge's rebase disabled; squash disabled unless squash is the chosen method; linear-history requirements off.
- Merge message: Git's subject or the pull-request title, never the description; the landing agent supplies the trailers where the API lets it.
- A merge queue or an up-to-date rule on every target that takes more than one pull request at a time.
- Delete head branches on merge.
