# Grounded Commits: landing

Format version 0.3.3. This part is optional: the commit and pull-request conventions work under any merge method. What is not optional is knowing what your method does to the commits, because they are the record: their messages, the trees their evidence lines describe, and their signatures. This document says what each method does and how to land so that what reaches the target is what was reviewed and checked.

## What landing has to preserve

1. **The commits.** The reviewed commits land as the objects they were reviewed as: same hashes, same trees, same messages, same signatures, or under squash the one landed message is composed from them. A method that replays them as new objects gives each a new commit and, wherever the target's change touches what a commit builds on, a new tree, so a `Verified: final contents` on the branch may describe a tree that was never tested, and every author signature is gone; the branch then owes a re-run or a rebinding per commit (the commit-message guidance, *After a rewrite*) and a re-signing, and the reviewers approved objects that no longer exist.
2. **The landed tree is checked.** Integrating a branch with a target that has moved produces a tree no branch commit has. That tree is checked before it lands, and the commit that carries it says so in its own `Verified:` line; where the forge makes the commit (GitHub's queue, GitLab's train), the evidence is the forge's run on it, read back at landing, and the commit carries no trailers.
3. **Nothing from the pull-request body enters history.** The body is a review brief. A merge commit the landing writes carries Git's subject, its evidence pair, the pull request's URL under `Refs:`, `Reviewed-by:` lines for the approvers and `Reviewed-on:` where the forge's template writes it, and a body only where it resolved something; one the forge makes carries the forge's default message.
4. **Issues close by hand after landing**, never by keyword.

## The integration candidate

The method that preserves all four lands a candidate built before landing: a merge commit `C` whose first parent is the target's tip `B` and whose second is the approved head `H`, made with `--no-ff` so that it exists even when `B` is already an ancestor of `H`. Its tree is the branch integrated into the target as the target stands. The landing agent builds it, runs the repository's checks on its tree, then writes its message (Git's subject; a trailer block with `Verified: final contents; <checks>; <outcome>`, `Refs: <pull request URL>`, `Reviewed-by:` lines for the approvers and `Reviewed-on:` where the forge's template writes it; a body only where a conflict was resolved, saying how) and signs it as the repository signs commits, which changes the commit's identity but not the tree the checks ran on; a check that reads commit ids, parents or tags runs after that finalisation. A candidate that resolved a conflict, or carries any edit beyond the merge, is reviewed before the target advances. If the target moved meanwhile, the advance is refused: build `C' = merge(B', C)`, the latest submitted candidate as its second parent, check it, try again; never force. When `B` is already an ancestor of `H`, `C`'s tree is `H`'s, so the checks that ran on `H` ran on the landed tree, and `C`'s `Verified:` line may name them as such.

Making the merge commit even then is deliberate: it gives `git log --first-parent` one commit per pull request, and it is the one place for the pull request's URL and the integration's evidence that needs no rewrite of a reviewed commit. A repository that prefers to fast-forward the target to `H` itself when `H` already contains `B` records that in its guidance; it then puts the pull request's URL on the branch's last commit before approval, since nothing is written afterwards, and lands a merge commit only for a branch that is behind.

A stacked pull request lands the same way: once its parent has landed, the child is retargeted to the target and its candidate is built from its own head, whose commits were never rewritten. A forge's own stacked-pull-request feature that rebases the stack at each landing is not used.

## Why not the other methods

- **Rebase, by the forge or by hand, then fast-forward.** Replays every commit: new hashes, new trees wherever the target's change touches what a commit builds on, author signatures dropped (a forge cannot sign with the author's key; a local rebase re-signs only with signing on, and plumbing such as `git commit-tree` ignores `commit.gpgsign` and signs only when passed `-S`), and every `Verified: final contents` rebound. Reviewers approved commits that are no longer what lands, and a re-check of the tip covers the tip alone. Linear history is all it buys.
- **Squash.** One new commit; every branch commit's message, evidence and signature is gone, and the trailer blocks of all but the last are buried in a body Git does not read as trailers. Supported where a repository wants one commit per pull request: the landing agent composes the message in the commit format from the branch's commits, with the evidence rebound to the landed tree, and supplies it explicitly, never the forge's default and never the pull-request body: on GitHub through the API's `commit_title` and `commit_message`, on Forgejo through `Do: squash` with `MergeTitleField` and `MergeMessageField`, on GitLab through `squash_commit_message`, each read back with `git show -s --format=%B`.
- **A merge the forge makes of a stale branch.** On GitHub the checks ran on a temporary merge of the head into the target as it stood when the run started, and the result was recorded against the head's hash; on Forgejo they ran on the head itself, which tested no integration at all. A target that moves afterwards re-runs nothing on either, so the merge the forge then makes has a tree nobody checked. That gap is why forges offer an up-to-date rule and a merge queue; without one of them it is open.

## Per forge

| Forge | Settings | Landing |
|---|---|---|
| **GitHub**, organisation-owned public repository, or private on Enterprise Cloud | Merge commits only; "Require linear history" off; the merge message the pull-request title only, never the description. A ruleset on the target: require a pull request; required status checks; "Require merge queue" with merge method *merge* and "Only merge non-failing pull requests"; block force pushes. Every required workflow triggers on `pull_request` and `merge_group`. On a public repository, check before enabling the queue whether `merge_group` runs fork-authored workflow changes with the base's secrets. | After approval, enqueue the approved head: `gh pr merge <n> --auto --match-head-commit <H>`, or the API's asynchronous merge with `sha` and `merge_action: merge_queue`; never a bypass. The queue builds the merge, runs the `merge_group` workflows on it and lands it; an enqueued state is not a landing, so wait for the merge. The queue's commit carries GitHub's message, so the agent adds no trailers; its evidence is the `merge_group` run, which the agent reads back beside the landed commit: the same hash means the checked object landed, which is observed for squash and not yet for merge; equal trees under different hashes is a claim about contents; neither is no evidence. |
| **GitHub**, user-owned repository or no queue | Merge commits only; require a pull request; required checks with "Require branches to be up to date before merging"; block force pushes. | Bring a branch that is behind current with "Update with merge commit", never "Update with rebase"; its merge's tree is then its head's, so the head's checks cover what lands, and approvals the update invalidated are given again. Run the gate on a local `merge(B, H)`, whose tree the up-to-date rule makes the landed tree, then land with `gh pr merge --merge --match-head-commit <H> --body-file <file>` whose file carries the trailer block, or the API's merge with `merge_method: merge`, `sha: <H>` and a `commit_message` carrying it: `Refs:`, `Reviewed-by:` and `Verified: final contents; <gate>; <outcome>` for that run. A landing without that line is not a checked landing. Each landing on a busy target invalidates every other open pull request's currency; a target taking several pull requests an hour wants a queue. |
| **Forgejo** (Gitea, its ancestor, was not checked; nothing here transfers to it) | Merge style *fast-forward-only* allowed and default; the repository's update style set to merge, which the instance's `DEFAULT_UPDATE_STYLE` sets only for new repositories. Branch protection: no direct push, or only the landing identity; required status contexts; required approvals; "Require signed commits" where the repository signs, which fast-forward-only satisfies without an instance key. | Build `C` locally, check it, sign it, push it to the pull-request branch (a fast-forward of `H`, which is its parent); the forge runs the pull-request workflows on `C` and records their statuses against it, and marks the reviews stale where a file's merged result differs from both sides. Land with `POST /repos/{owner}/{repo}/pulls/{index}/merge`, `Do: fast-forward-only`, `head_commit_id: <C>`, no `force_merge`. The forge refuses a branch that is behind, in which case build `C' = merge(B', C)`, check and push it, and ask again; it advances the target to the candidate exactly, so read back that `merge_commit_sha` is that commit and that the target moved. A fork the agent cannot push to: publish `C` on a maintainer-owned branch and land it by the same steps through its own pull request, the contributor's commits preserved as its second parent and the original pull request's URL in its trailers, then mark the original merged by hand through the same endpoint with `Do: manually-merged` and `MergeCommitID: <the landed commit>`; or ask the contributor to push a current head. |
| **GitLab** | Merge method *fast-forward*, automatic rebase off, squash "Do not allow", "Pipelines must succeed"; or, on Premium or Ultimate with a busy target, merge commits with merged results pipelines and merge trains, the merge template without the automatic issue-closing text. | Fast-forward: stage `C` on the source branch as on Forgejo, let the pipeline run on it, land with `PUT …/merge` and `sha: <C>`; GitLab refuses unless the candidate contains the target's tip. Trains: add with `auto_merge`, never "merge immediately"; the landed merge is a fresh object whose tree equals the train's checked tree because the train serialises the target, or the pipeline's own commit where the train lands its ref, so read back the pipeline's hash and tree beside the landed ones; set the train's enforcement so that no merge bypasses it, and restrict direct pushes to the target. Not automatic rebase before merge, which strips signatures and runs no pipeline on its result; not an explicit rebase of the source, which rewrites the reviewed objects; not fast-forward or semi-linear trains, whose candidates are rebased. |
| **Plain Git**, no forge gate | — | On the target's tip, `git merge --no-ff --no-commit <H>`, run the checks, then commit with the message and push; a refused push means the target moved, so rebuild from its new tip with the candidate as second parent. |

Enable only the method your repository uses, so an agent cannot pick another. Whenever a forge makes the landing commit, read its message back (`git show -s --format=%B`, `git interpret-trailers --parse --no-divider`) and confirm the approved head is an ancestor of the landed tip: its second parent under a merge, the tip itself after a fast-forward; under squash, that the landed tree is the checked tree.

## Pull requests from forks

A fork's commits may not follow the format, and the contributor's branch may not accept the maintainer's push. Record one route in guidance: land the contributor's commits as written through a candidate on a maintainer-owned branch, which preserves their objects; squash with a message composed in the format, the usual route for drive-by contributions; or ask the contributor to fold and reword. Whatever the route, the forge must record the pull request as merged: GitHub does so when the head's commits become reachable from the base, Forgejo when the merge goes through its interface or API.

## Forge configuration, in short

- The method of your forge's row enabled and every other disabled: merge commits on GitHub, fast-forward-only on Forgejo, fast-forward or merge trains on GitLab; the forge's rebase off everywhere; squash only where squash is the chosen method; linear-history requirements off.
- Merge message: Git's subject or the pull-request title, never the description; the landing agent supplies the trailers where the API lets it.
- A merge queue or an up-to-date rule on every target that takes more than one pull request at a time.
- Delete head branches on merge.
