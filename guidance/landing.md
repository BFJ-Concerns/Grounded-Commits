# Grounded Commits: landing a branch

Format version 0.3.0. This part is optional: the commit and pull-request conventions work under any merge method. What is not optional is knowing what your method does to the commit messages, because they are the record. This document says what each method does and how to keep the record intact under it.

## What landing has to preserve

1. **The record.** Under fast-forward and merge commits, each commit's message lands as written, or as deliberately reworded before landing; under rebase the same, except that GitHub drops a commit that was empty to begin with, message included, and on Forgejo and Gitea a template that applies cannot amend such a commit at the tip; so before landing by rebase, fold such a commit's message into a neighbour, which leaves every tree as reviewed; giving it content instead changes the tree after approval. Under every method, the rebase that prepares the branch drops a commit whose change the target already carries, with a warning for an identical patch and silently where the change arrived another way; its message goes with it, since the branch no longer delivers that change, so carry any reasoning that still matters into a neighbour's body and name the commit in the landing comment. Under squash, the branch's messages are replaced by one message composed from them; the composition is deliberate, never the forge's default.
2. **Nothing from the pull-request body enters history.** The body is a review brief.
3. **What lands is what was reviewed.** The landing comment names the reviewed head and says whether the landing tip's tree and messages still match it, with any evidence collapsed (the pull-request guidance, *Before landing*).
4. **Issues close by hand after landing**, never by keyword.

Whenever a method rewrites commits, read the landed messages back (`git log --format=%B <range>`) and compare them with what was pushed.

## Choosing a method

The default is **fast-forward**: the prepared tip, re-checked and carrying the approvals the forge requires, becomes the target's history unchanged, same hashes, same signatures, so what landed is that tip, by identity. It needs the branch to sit on the target's current tip, which is the rebase and re-check that *Before landing* already asks for; a push refused because the target moved again means rebasing and re-checking again, not another method. **Rebase** is the fallback for a repository whose forge cannot fast-forward, which on GitHub means its landing identity may not push to the target: a choice the repository makes once and records in its guidance, never a retry when a push fails. What the forge then does differs. GitHub always replays the commits as new objects, keeping every message except that of a commit it drops for having been empty to begin with, so hashes and signatures are lost. Forgejo and Gitea rebase only a branch that is behind and fast-forward one that is current, amending the last commit only where a merge template applies, so a current branch with no applicable template lands unchanged there. GitLab's rebase from the UI is server-side and drops signatures. A repository that signs its commits therefore does not take the rebase route on GitHub, and on Forgejo and Gitea prefers *Fast-forward only*, which reads no template, refuses a branch that is behind, and for a current branch lands what *Rebase* would land with no applicable template; where it cannot fast-forward, it gives the landing identity permission to push, or lands by merge commit. Merge commits and squashes are supported with the configuration below. Enable only the method your repository uses, so an agent cannot pick another.

| Method | What happens to the commits | Configure | Watch for |
|---|---|---|---|
| **Fast-forward** (default) | Land unchanged: same hashes, same signatures. | GitLab: merge method *Fast-forward merge*, squash *Do not allow*, and automatic rebase before merge off, since that rebases server-side at merge time, drops signatures and runs no pipeline on the result. Forgejo and Gitea: merge style *Fast-forward only*. Plain Git: `git merge --ff-only`. GitHub has no button; see below. | The branch must already sit on the target's tip, so rebase and re-check before landing. GitLab's rebase from the UI is a server-side rebase that drops signatures, so a signing repository rebases locally. |
| **Rebase** (fallback) | Replayed onto the target by the forge as new commits with the same messages: on GitHub always, with new hashes, the committer updated, signatures not carried and originally empty commits dropped; on Forgejo and Gitea only when the branch is behind or a template rewrites the last message, a current branch landing unchanged. | GitHub: *Rebase and merge*. GitLab: not needed, since its fast-forward setting above serves. Forgejo and Gitea: *Rebase*, with no merge template that applies, or one that keeps `${CommitTitle}` and `${CommitBody}` and omits the description. Both read templates from the base repository's default branch: Gitea `.gitea/default_merge_message/REBASE_TEMPLATE.md`, then its `DEFAULT_TEMPLATE.md` fallback; Forgejo reads the same file under `.forgejo/` or `.gitea/`, then the instance's own, which the repository cannot see, and an empty template file still yields the default message. Any template that applies amends the last commit, even to the same text, which replaces any author signature on it (Gitea signs the amend with the instance key where it signs; Forgejo's amend passes no signing option), so read the landed messages back. | Land only a linear branch rebased onto the target's current tip, so the replay reproduces the prepared branch's trees exactly: the tip's tree is the one the checks ran on, and each commit's evidence, including any declared gap, still describes what lands. A branch brought up to date by merging the target into it does not qualify. GitHub's *Require branches to be up to date before merging* and Forgejo's and Gitea's *Block merge if pull request is outdated* enforce currency but accept such a merge, so update by rebase. A `Verified:` line that names a branch commit by hash still names what was tested; it need not stay reachable. After a replay the source branch is not an ancestor of the target, so delete it on merge. |
| **Merge commit** | Land unchanged, plus a merge commit. | Set the merge message to the pull-request title only: GitHub *Default to pull request title*; Forgejo and Gitea `MERGE_TEMPLATE.md` without `${PullRequestDescription}`; GitLab merge commit template `%{title}`. | A merge message that includes the description puts the brief into history. Land the branch current, like any other, so the merge commit's tree is the tip the checks ran on. |
| **Squash** | Replaced by one new commit. | The landing agent composes the squash message in the commit format from the branch's commits (problem, approach, `Considered and rejected:`, limits, evidence rebound to the landed tree) and supplies it explicitly: GitHub API `commit_title` and `commit_message`, or the repository's squash-message setting; GitLab `squash_commit_message`; Forgejo's and Gitea's merge title and message fields. Never the forge's default. | Read the landed message back with `git show -s --format=%B` and `git interpret-trailers --parse --no-divider`. Each commit's own account is gone; only the composed one remains. Land the branch current, like any other. |

### Fast-forward on GitHub

GitHub's *Rebase and merge* "always updates the committer information and creates new commit SHAs", and the merge queue only merges, rebases or squashes. To land the hashes unchanged, push the approved, rebased tip to the target yourself: `git push origin <tip>:main`. GitHub then marks the pull request merged, because its head commits have become reachable from the base. Whether the push is allowed depends on the protection in force: required status checks permit a direct push of a commit whose checks passed; required reviews and push restrictions permit it only to an identity they allow. Where the push goes around a protection, the landing step is doing that protection's job, so confirm approval and passing checks on that exact tip before pushing. A repository whose landing identity may not push chooses rebase as its method once, as *Choosing a method* says; a refusal at landing time is reported, never answered by switching method.

## Pull requests from forks

A fork's commits may not follow the format, and a squash rewrites them anyway, as a rebase may. Whatever the route, the prepared branch must become the pull request's head, since the forge lands, or records as merged, that head: push it to the contributor's branch where they allow edits from maintainers (GitHub permits this on user-owned forks), or ask them to push it. Pick one route and record it in guidance:

- **Rebase** the fork's commits as written when their messages are acceptable.
- **Squash** with a message composed in the format when they are not. This is the usual route for drive-by contributions.
- **Reword** the commits when their messages need it; the forge then lands them by the repository's method.

## Settings worth setting

- Default merge message: pull-request title only, never the description.
- Squash: disabled unless squash is the chosen method.
- Delete head branches on merge.
- Review bots that write summaries into the description: comment mode.
- Agent tools: point their guidance at the pull-request guidance so the shipped template is replaced.
